一、项目概述

本项目以巴西领先电商平台 Olist 公开发布的电商订单数据集为研究对象，模拟企业"用数据驱动运营决策"的真实场景，独立完成一条从数据采集 → 清洗 → 探索性分析（EDA）→ 业务分析 → 可视化的端到端数据分析流水线。

项目目标不是简单"画几张图"，而是回答电商运营中最常被追问的五类业务问题：销售趋势与季节性、用户价值分层、品类结构、区域分布、交付与体验，并最终沉淀为可复用的分析框架与方法论，体现"从数据到业务决策"的闭环思维。

1.2 数据集与关键指标

数据集包含 9 张原始表（订单、客户、商品、卖家、支付、评价、地理等），经清洗聚合为订单粒度的分析宽表。核心规模指标如下：

总营收（R$ 雷亚尔）
订单总数
独立客户数
平均客单价（R$）
平均评分（满分 5）
时间跨度（月）

数据时间跨度： 至 ；已送达订单准时/提前交付率 %，取消/不可用订单 单。

二、数据源与采集方案

2.1 为什么选公开数据集而非自行爬取

国内主流电商平台（淘宝/京东/拼多多）的用户协议普遍禁止未经授权的自动化采集，且大多需要登录、带有反爬机制；直接爬取既存在合规与法律风险，也难以稳定获取高质量数据。因此本项目选用 Kaggle 公开数据集 Olist Brazilian E-Commerce——由平台官方发布、授权协议为 CC BY-NC-SA 4.0（署名-非商业-相同方式共享），数据真实、字段完整、可合法用于学习与作品集展示。

合规优先原则：用"公开授权数据"替代"爬商业站点"，既不触碰《个人信息保护法》与平台协议红线，又能完整跑通数据分析方法论，分析框架可平移到真实业务。

2.2 采集方式

  • 使用 kagglehub 库匿名下载公开数据集（无需 Kaggle 账号、无需 API Token、免费）；
  • 下载落盘到 data/olist/ 作为原始层，与清洗层、分析层分离，符合数据分层治理规范；
  • 首次下载后走本地缓存，重复运行不重复下载，便于复现。

三、数据预处理与清洗

原始数据分散在多张表中，且时间格式、缺失值、重复坐标等问题并存。清洗目标是把 9 张表围绕"订单"主键聚合成一张可直接分析的统一宽表（olist_orders_clean.csv，99,441 行 × 17 列）。

3.1 主要清洗步骤

  1. 读取与筛选：只取分析相关的 7 张表，降低内存压力；
  2. 时间解析：5 个时间字段统一转为 datetime，脏数据用 coerce 转为缺失（不让脚本中断）；
  3. 明细聚合：按订单汇总 price/freight 求和、件数计数、类目取众数（top_category）；
  4. 支付聚合：每单累计实付 total_paid、支付笔数、主要支付方式（众数）；
  5. 评价聚合：每单平均评分 avg_review_score；
  6. 宽表组装：以 order_id 左连接客户 / 明细 / 支付 / 评价维度；
  7. 派生指标：delivery_delay_days = 实际送达 − 预计送达（正=迟到，负=提前）。

3.2 缺失值说明（业务事实，而非程序错误）

字段缺失量业务含义与处理
order_delivered_customer_date2,965 行未送达订单（取消/在途等），交付分析时按 order_status 过滤
top_category775 行少量订单无商品类目，标记为 unknown 处理
avg_review_score768 行无评价订单，保留缺失，评分分析时排除

3.3 数据分层

项目全程遵循 原始层(data/olist) → 清洗层(data/clean) → 分析层(data/analysis) → EDA 层(data/eda) 的分层规范，每一层可追溯、可复现，也是企业数据治理的基本习惯。

四、探索性数据分析（EDA）

本阶段基于清洗宽表，用 describe() 做描述统计、用 groupby() 做多维度分组统计，并通过图表把"数字"翻译成"业务语言"。每张图下方均标注图表类型、坐标轴与业务意义，便于面试时解释。

图 1 · 月度销售额与订单量趋势　类型：双轴折线图｜X 轴：月份（2016-10 ~ 2018-08 主周期）｜左 Y 轴：月营收（R$）；右 Y 轴：月订单数。
业务意义：识别销售增长趋势、季节性峰谷与异常月份，为库存排期与营销节奏提供依据。

数据解读：营收与订单量整体呈上升趋势，2017-11 出现明显峰值（约 R$119 万、7,544 单），对应巴西年末大促（类似双十一）；2018 年上半年维持高位平台期。首尾月份（2016-09、2018-09/10）数据量极小，属数据集截取边界，分析时已剔除，避免误导结论。

图 2 · 支付方式占比　类型：环形图｜维度：支付方式｜数值：订单数占比。
业务意义：衡量支付渠道集中度，关系到结账转化率、手续费成本与信用卡欺诈风控优先级。

数据解读：信用卡（credit_card）占 76.6%，渠道高度集中；其次是 Boleto 账单（约 20%）。集中度过高提示：① 信用卡到账与欺诈风控是重点；② 优化 Boleto 等替代支付可覆盖无信用卡人群、提升转化。

图 3 · 品类营收 Top10　类型：横向柱状图｜Y 轴：品类（中文）｜X 轴：营收（R$）。
业务意义：识别品类贡献度，支撑选品、库存与营销资源倾斜（帕累托分析）。

数据解读：营收第一品类为健康美容（health_beauty，9.0%），其后为手表礼品、床品卫浴、运动休闲、电脑配件。Top10 品类合计贡献约六成营收，长尾品类众多——符合电商"少数头部品类撑起主要 GMV"的典型结构。

图 4 · 州营收 Top10　类型：柱状图｜X 轴：客户所在州｜Y 轴：营收（R$）。
业务意义：刻画区域集中度，指导区域仓配布局与本地化营销优先级。

数据解读：营收高度集中于东南沿海——圣保罗州（SP）一家占 37.5%，里约（RJ）、米纳斯（MG）次之。三州合计超六成，提示物流与营销资源应向东南区域倾斜，同时中西部/北部州客单价反而偏高（如 PB、AC），存在差异化机会。

图 5 · 用户评分分布　类型：柱状图｜X 轴：评分（1~5 分 + 无评价）｜Y 轴：订单数。
业务意义：评估整体满意度形态，定位差评来源以驱动品控与售后回流。

数据解读：评分呈"高分集中"形态：5 分占 57.3%、4 分占 19.1%，全局平均 4.09。但仍有约 14.5% 的订单给出 ≤2 分的差评（1 分占 11.4%），这部分是体验优化与差评回访的重点群体。

图 6 · 交付延迟 × 评分 交叉热力图　类型：热力图｜X 轴：评分档｜Y 轴：交付延迟档｜色深：订单数。
业务意义：检验"物流时效是否影响用户体验"的核心假设，是本项目最具行动价值的一张图。

数据解读：颜色梯度清晰显示：提前/准时交付的订单大量集中在 4~5 分；而严重迟到（>7 天）的订单中 77.1% 给了低分（≤2 分）。假设被验证——交付时效是用户体验的关键瓶颈，物流履约优化应优先于单纯投放拉新。

图 7 · RFM 用户分层　类型：柱状图｜X 轴：客户分群｜Y 轴：客户数。
业务意义：用最近消费(Recency)、频次(Frequency)、金额(Monetary)把客户分层，支撑差异化运营。

数据解读：96,096 名客户分为五群，结构较均衡：一般客户 34,575、沉睡 15,463、新客/潜力 15,389、重要价值 15,376、流失风险 15,293。重点动作：对"重要价值"客户做留存与会员化，对"流失风险/沉睡"客户做唤醒召回。

五、业务结论与项目价值

5.1 面向求职落地的四条业务结论

  1. 物流时效是体验第一瓶颈。严重迟到订单 77% 转化为差评，验证"履约 > 拉新"。建议：对 >7 天交付订单建立预警与补偿机制，优先提升准时率（当前已送达订单准时率约 94%，仍有少量迟到空间）。
  2. 区域高度集中，需"保核心+探差异"。SP/RJ/MG 三州贡献超六成营收，仓配与营销应聚焦东南；而 PB、AC 等小州客单价更高，可差异化选品提高毛利。
  3. 品类头部效应明显，长尾需精细化。健康美容等 Top10 品类撑起约六成 GMV；长尾品类众多但单量低，适合用"捆绑/关联"策略提升客单价，而非盲目扩品类。
  4. 客户结构健康但唤醒价值大。重要价值客户约 1.5 万，同时存在约 3 万沉睡/流失风险客户。RFM 分层可直接转化为"留存 vs 召回"两套运营动作，而非大水漫灌。

5.2 项目价值

  • 工程价值：独立完成"采集→清洗→EDA→分析→可视化"全链路，代码可运行、数据分层可追溯、仓库可复现；
  • 业务价值：不堆图表，而是从数据提炼出可落地的运营建议（物流、区域、品类、客户四线）；
  • 合规价值：全程使用公开授权数据，规避爬虫法律风险，方法论可平移到国内业务；
  • 表达价值：产出交互看板与本报告，可直接作为作品集与面试讲解素材。

六、项目总结、局限性与后续优化方向

6.1 总结

本项目以公开电商数据集为载体，完整呈现了一名大数据专业学生应具备的"数据工程 + 数据分析 + 业务解读 + 可视化表达"综合能力，并强调合规采集与数据分层治理的职业习惯。

6.2 局限性

  • 外部有效性有限：数据来自巴西市场、2016–2018 年，与国内电商在品类、支付、物流上差异明显，结论不能直接套用，但分析框架通用；
  • 时间跨度不足以支撑长期预测：约 25 个月、且首尾不完整，未做时序预测建模（仅做描述/诊断）；
  • 缺少用户画像与营销标签：无年龄、性别、渠道来源等，归因存在盲区（如差评是否由商品质量导致无法完全分离）；
  • 单机中小规模：未覆盖生产级分布式（Hadoop/Hive/Spark），以方法论演示为主。

6.3 后续可优化方向

  1. 引入 Apriori 购物篮分析，挖掘品类关联与捆绑推荐（基于 order_items 共现）；
  2. 用 geolocation 表计算城市经纬度，做订单地理热力/地图可视化；
  3. 把 RFM 升级为标准 8 分群矩阵并画热力图，增强用户分层粒度；
  4. 接入 MySQL + 调度，把单机脚本升级为可定时更新的分析管道；
  5. 补充时间序列预测（Prophet/ARIMA），从诊断分析走向预测分析。
